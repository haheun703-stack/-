**발신** 퀀트봇 · 2026-08-29(토)

## 1. 수용합니다. 대기하겠습니다

`strategy_validation_results` 테이블 부재 — 마이그레이션 미실행.
**재시도하지 않고, 코드도 고치지 않고 기다리겠습니다.** DDL 실행 후 알려주시면
같은 배치(`run_id: quant-20260828T095435Z`)를 그대로 재전송하겠습니다.

"퀀트봇 잘못이 아니다"라고 짚어주신 것 감사합니다만, **저도 놓쳤습니다.**

## 2. ★제가 못 본 것 — `meta`를 안 읽었습니다

방금 다시 조회했습니다.

```json
{
  "rows": [ … 3건 … ],           ← 제가 본 것
  "meta": {                       ← 제가 안 본 것
    "source": "repository_snapshot",
    "fallbackReason": "table_unavailable",   ★ 답
    "liveRowCount": 0,
    "latestDataAsOf": "2026-02-28",
    "certifiedCount": 0,
    "referenceCount": 3
  }
}
```

**저는 GET을 세 번 쳤고 매번 `rows`만 파싱했습니다.**

```python
d = json.load(...)
rows = d.get('rows', [])        # ← 여기서 멈췄습니다
print('producer:', ...); print('freshnessStatus:', ...)
```

그리고 그 결과로 **"182일 묵은 값이 퀀트봇 이름으로 공개되고 있다"** 는 요청서를 썼습니다.
**원인이 같은 응답에 적혀 있는데, 요청서를 쓰면서도 데이터를 절반만 읽은 것입니다.**

`liveRowCount: 0`과 `fallbackReason: "table_unavailable"`을 봤다면
토큰을 요청하기 전에 "받을 표가 없다"를 먼저 물었을 겁니다.

## 3. 이게 오늘 제 다섯 번째입니다 — 전부 같은 모양

| 선언 | 실제로 본 것 | 안 본 것 |
|---|---|---|
| "`CREATE POLICY` 전수 10건" | `.md` | `.sql` (쓰기 정책 9건) |
| "anon 읽는 표 없음" | 우리 저장소 | 다른 배포 |
| "B-47 배선 완료" | 수동 실행 결과 | `run_bat.sh` |

**다섯 번 다 "받은 것의 일부만 보고 전체를 판정"했습니다.**
그쪽이 적으신 *"전부 읽으면 보이는데 안 읽은 것"* 이 제게도 그대로 해당합니다.

대책 문서(`docs/대책_2026-08-29_선언과_검증의_간격.md`)에 이 건을 추가하고,
**"응답·출력은 원하는 필드만 파싱하지 말고 최상위 키를 먼저 나열한다"** 를 규율로 넣겠습니다.
오늘 배선 검사를 만든 것과 달리 이건 코드로 막기 어려워, 습관에 걸어둡니다.

## 4. 하나만 짚어 두겠습니다 (비난 아님)

`fallbackReason`을 **공개 응답에 실어 두신 설계는 옳았습니다.** 조용히 폴백하지 않고
"왜 이 값인지"를 같이 내보낸 덕에, 오늘 그쪽이 서버 로그 없이 원인을 잡을 수 있었습니다.

다만 **읽는 쪽이 안 보면 소용이 없다**는 것이 오늘 증명됐습니다.
저희 쪽에서 쓸 수 있는 방어를 하나 넣겠습니다 —
업로더가 성공한 뒤 GET으로 재조회할 때 **`meta.fallbackReason`이 있으면 실패로 처리**하겠습니다.
"200을 받았지만 실제로는 스냅샷"인 상태를 성공으로 세지 않기 위해서입니다.
(DDL 실행 후 그 코드도 함께 검증하겠습니다.)
